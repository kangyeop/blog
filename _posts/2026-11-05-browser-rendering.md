브라우저가 화면을 그리는 원리는 프론트엔드를 처음 공부할 때 한 번 정리해본 적이 있다. 그런데 개발을 하다 보니 리플로우, 리페인트 같은 단어만 남고 그 안에서 실제로 무슨 일이 일어나는지는 흐릿해졌다. HTML이 화면에 그려지기까지의 과정을 다시 한번 정리해보려고 한다.

## 브라우저의 구조

Chrome을 켜고 작업 관리자를 열어보면 Chrome 항목이 여러 개 떠 있다. Chrome은 하는 일을 나눠서 여러 **프로세스**로 따로 실행한다. 주소창과 탭을 그리는 브라우저 프로세스, 웹 페이지를 그리는 렌더러 프로세스, 화면에 최종 결과를 내보내는 GPU 프로세스 등이다. 렌더러 프로세스는 사이트마다 따로 떠서, 한 사이트가 멈춰도 다른 탭은 멀쩡하다.

웹 페이지를 그리는 일은 렌더러 프로세스의 **메인 스레드**가 거의 다 한다. HTML 파싱, 스타일 계산, 레이아웃, 페인트, 그리고 자바스크립트 실행까지 같은 스레드에서 한다. 자바스크립트가 오래 돌면 화면이 멈추는 이유가 이것이다. 메인 스레드 말고 **컴포지터 스레드**도 있는데, 이 스레드는 메인 스레드가 그려둔 결과를 합쳐서 프레임을 만든다.

## 화면을 그리는 단계

1. **파싱**: HTML로 DOM을 만들고 CSS를 읽는다.
2. **스타일 계산**: 요소마다 최종 스타일을 정한다.
3. **레이아웃**: 요소마다 위치와 크기를 계산한다.
4. **페인트**: 무엇을 어떤 순서로 그릴지 정한다.
5. **합성**: 레이어별로 그린 결과를 합쳐 한 장의 화면을 만든다.

파싱부터 페인트까지는 메인 스레드에서, 합성은 컴포지터 스레드에서 한다. 이 흐름을 **렌더링 파이프라인**이라고 한다.

## HTML 파싱과 DOM

브라우저는 HTML을 읽어서 **DOM** 트리를 만든다. HTML을 다 받을 때까지 기다리지 않고 받는 대로 조금씩 파싱한다.

파싱 중에 `<script>`를 만나면 파싱을 멈추고, 스크립트를 받아서 실행한 뒤에야 다음 줄로 넘어간다. 스크립트가 DOM을 바꿀 수 있기 때문이다. `defer`나 `async`를 붙이면 파싱과 동시에 스크립트를 받는다.

| 속성 | 실행 시점 | 실행 순서 |
| --- | --- | --- |
| 없음 | 받자마자, 파싱을 멈춘 채로 | 문서 순서 |
| `defer` | 파싱이 끝난 뒤 | 문서 순서 |
| `async` | 받자마자 | 받는 순서 |
| `type="module"` | `defer`와 같음 | 문서 순서 |

Vite 앱의 `<script type="module">`이 `<head>`에 있어도 파싱을 막지 않는 건 모듈 스크립트가 기본으로 `defer`처럼 동작하기 때문이다.

파서가 멈춰 있는 동안에는 **프리로드 스캐너**가 뒤쪽 HTML을 미리 훑어서 이미지나 스타일시트 요청을 먼저 보낸다. 다만 HTML에 직접 적힌 리소스만 찾는다. 자바스크립트로 나중에 넣는 이미지나 CSS `background-image`는 늦게 요청된다.

## CSS와 스타일 계산

`<head>`의 스타일시트는 **렌더링을 막는다**. 브라우저는 CSS를 다 받기 전까지 화면을 그리지 않는다. 스타일 없는 화면이 먼저 보였다가 바뀌는 깜빡임을 막으려는 것이다.

CSS를 받으면 **스타일 계산**을 한다. 요소마다 해당하는 규칙을 찾고, 규칙끼리 겹치면 명시도와 순서로 하나를 고르고, 상속까지 반영해서 최종 값을 정한다. 개발자 도구 Elements 패널의 Computed 탭에 보이는 값이 이 결과다.

## 레이아웃

**레이아웃**은 요소마다 위치와 크기를 계산하는 단계다. 화면에 박스로 그려지는 것만 대상이라 `display: none`인 요소는 빠지고, `visibility: hidden`인 요소는 보이지 않아도 자리를 차지하니 포함된다.

레이아웃은 비싸다. 요소 하나의 높이가 바뀌면 아래 형제들이 밀리고 부모 높이도 바뀔 수 있어서, 변경이 주변으로 번진다.

## 페인트와 합성

**페인트**는 픽셀을 바로 칠하는 게 아니라 "여기에 사각형, 저기에 글자" 같은 그리기 명령 목록을 만드는 단계다. 나중에 그린 게 위에 보이는데, 이 순서는 `z-index`와 쌓임 맥락으로 정해진다.

브라우저는 페이지를 한 장으로 그리지 않고 여러 **레이어**로 나눠서 그린다. `transform`이나 `opacity` 애니메이션이 걸린 요소, `will-change`를 준 요소, `<video>` 같은 요소가 따로 레이어가 된다. **합성**은 이 레이어들을 겹쳐서 한 장의 화면을 만드는 단계다.

합성은 컴포지터 스레드가 하기 때문에 메인 스레드가 바빠도 동작한다. 스크롤과 `transform`, `opacity` 애니메이션이 자바스크립트가 무거울 때도 부드러운 이유다. 다만 레이어마다 메모리를 쓰니 `will-change`를 아무 데나 붙이면 오히려 느려진다.

## 무엇을 바꾸면 어디부터 다시 할까

바뀐 속성에 따라 브라우저가 다시 하는 단계가 다르다.

| 바꾼 것 | 다시 하는 단계 |
| --- | --- |
| `width`, `height`, `margin`, `top`, 텍스트, DOM 추가·삭제 | 레이아웃 → 페인트 → 합성 |
| `color`, `background-color`, `box-shadow` | 페인트 → 합성 |
| `transform`, `opacity` | 합성 |

레이아웃을 다시 하는 걸 **리플로우**, 페인트를 다시 하는 걸 **리페인트**라고 부른다.

그래서 요소를 움직일 때는 `left`보다 `transform`을 쓴다. `left`를 바꾸면 매 프레임 레이아웃부터 다시 하고, `transform`은 이미 그려둔 레이어를 옮기기만 한다.

```css
/* 매 프레임 레이아웃부터 다시 한다 */
@keyframes slide-left {
  from { left: 0; }
  to { left: 100px; }
}

/* 매 프레임 합성만 한다 */
@keyframes slide-transform {
  from { transform: translateX(0); }
  to { transform: translateX(100px); }
}
```

## 강제 동기 레이아웃

브라우저는 스타일이 바뀔 때마다 바로 레이아웃을 하지 않고, 모아뒀다가 다음 프레임을 그리기 전에 한 번에 한다. 그런데 자바스크립트가 `offsetHeight`나 `getBoundingClientRect()`처럼 레이아웃 결과를 읽으면, 정확한 값을 주려고 그 자리에서 레이아웃을 한다. 이걸 **강제 동기 레이아웃**이라고 한다.

반복문에서 쓰기와 읽기를 섞으면 이게 매번 일어난다.

```js
// 반복마다 레이아웃이 일어난다
for (const item of items) {
  item.style.width = container.offsetWidth + 'px';
}

// 읽기를 밖으로 빼면 한 번만 일어난다
const width = container.offsetWidth;
for (const item of items) {
  item.style.width = width + 'px';
}
```

읽기를 먼저 다 하고, 쓰기를 나중에 몰아서 한다.

## 프레임과 requestAnimationFrame

60Hz 모니터는 1초에 60번, 약 16.6ms마다 화면을 바꾼다. 브라우저는 이 안에 자바스크립트 실행부터 합성까지 끝내야 화면이 끊기지 않는다. 자바스크립트 작업 하나가 50ms를 넘기면 그동안 화면을 그리지 못하고, 클릭해도 반응이 늦어진다.

`requestAnimationFrame`은 다음 프레임을 그리기 직전에 콜백을 실행한다. 화면을 바꾸는 코드는 `setTimeout`보다 여기에 두는 게 프레임과 정확히 맞는다.

## React와 이어서 보기

React의 커밋도 결국 이 파이프라인 위에서 일어난다.

1. React가 커밋 단계에서 DOM을 바꾼다.
2. `useLayoutEffect`가 실행된다.
3. 브라우저가 스타일 계산, 레이아웃, 페인트, 합성을 한다.
4. `useEffect`가 실행된다.

1과 2 사이에 브라우저는 화면을 그리지 못한다. 그래서 `useLayoutEffect`에서 `getBoundingClientRect()`로 크기를 재고 state를 바꾸면, 그 결과가 반영된 화면이 처음부터 그려진다. 툴팁 위치를 잡을 때 `useLayoutEffect`를 쓰는 이유다. 반대로 여기서 시간이 오래 걸리면 그만큼 화면이 늦게 뜨니, 이런 경우가 아니면 `useEffect`를 쓴다.

## 개발자 도구로 확인하기

- **Performance 패널**: 녹화하면 Layout, Paint가 언제 얼마나 걸렸는지 보인다. 강제 동기 레이아웃은 "Forced reflow" 경고로 표시된다.
- **Rendering 탭**: Paint flashing을 켜면 다시 페인트되는 영역이 초록색으로 깜빡인다.
- **Layers 패널**: 레이어가 몇 개이고 왜 생겼는지 보인다.
