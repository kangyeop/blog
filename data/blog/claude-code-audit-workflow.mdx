팀에 합류했을 때는 이미 프로젝트가 어느 정도 진행되어 있었다. 온보딩하면서 코드를 보는데 안 쓰는 컴포넌트, 뒤섞인 폴더 구조, 파일마다 제각각인 컨벤션이 꽤 쌓여 있었다. 그런데 합류하자마자 요청이 계속 들어오고 바뀌었고, 그에 맞춰 빠르게 대응하는 게 우선이다 보니 이런 코드를 정리할 여유가 나지 않았다. 대응만 하다 보니 이런 코드가 계속 쌓이는 거였다는 걸 알게 됐고, 매번 손으로 훑어보는 대신 Claude Code에 감사(audit)를 맡기는 방향으로 가보기로 했다.

## 감사부터 PR까지

온보딩 때 확인한 문제가 안 쓰는 컴포넌트, 뒤섞인 폴더 구조, 제각각인 컨벤션 이렇게 세 갈래였던 만큼, 감사도 처음부터 세 가지 워크플로우로 나눠 시작했다. 각각 GitHub Action으로 정해진 시간대에 스케줄이 실행되면 Claude Code가 감사를 수행하고, 결과를 PR로 자동 생성한다.

세 워크플로우가 보는 대상은 다음과 같다.

- **죽은 코드 제거**: 어디서도 참조되지 않는 컴포넌트, 함수, export를 찾아 지운다.
- **FSD 감사**: 레이어 경계를 넘는 import나 잘못된 위치에 있는 파일을 찾는다.
- **컨벤션 체크**: 파일명 규칙처럼 ESLint 같은 정적 도구로는 안 잡히는 부분을 본다. ESLint가 이미 걸러내는 규칙은 감사 범위에서 제외했다.

돌리기 시작하고 나서는 꽤 쓸만했다. 매번 손으로 훑어보진 못해 놓쳤던 죽은 코드를 찾아 지웠고, 컨벤션을 어긴 파일들도 하나씩 잡아냈다.

## 죽은 코드인데 죽은 코드가 아니었던 경우

이렇게 돌아가던 워크플로우에서 문제가 하나 생겼다. 죽은 코드 제거를 돌리다가 실제로 쓰이고 있는 export가 삭제 대상으로 올라온 적이 있다. 워크플로우가 이 export를 어디서도 참조하지 않는다고 판단해서 지워버린 것이었다.

이 PR은 GitHub Actions 기본 `GITHUB_TOKEN`으로 만들어졌다. `GITHUB_TOKEN`으로 생성한 PR은 재귀 실행을 막기 위해 `pull_request` 이벤트로 새 워크플로우를 트리거하지 않는다. 그래서 CI가 아예 돌지 않았고, 오탐이 자동으로 걸러지지 못한 채 그대로 머지됐다. 문제는 이후 빌드와 런타임에서 터지고 나서야 드러났다.

grep이나 텍스트 기반 참조 탐색은 문자열이 코드 어딘가에 등장하는지만 본다. 그러다 보니 타입으로만 연결되어 있거나, 동적으로 조립되는 경로처럼 텍스트 매칭으로 잡히지 않는 참조는 놓친다.

## serena 도입

이 한계를 넘어서려면 문자열 매칭이 아니라 코드 구조 자체를 이해하는 도구가 필요했다. 팀원이 이 오탐을 짚어주면서 serena를 제안했고, 그렇게 도입하게 됐다.

serena는 LSP 기반으로 심볼 단위 검색·편집 도구를 제공하는 MCP 툴킷이다.

serena가 내부적으로 쓰는 TypeScript 언어 서버(LSP)가 노출하는 기능은 에디터에서 "정의로 이동"이나 "모든 참조 찾기"를 눌렀을 때 동작하는 것과 같다. `textDocument/references`, `textDocument/definition` 같은 LSP 메서드가 그 기능을 담당하는데, 문자열 매칭이 아니라 TypeScript 컴파일러가 만든 AST와 타입 정보를 기준으로 답한다. 그래서 타입으로만 연결된 참조, 배럴 파일을 통한 재수출, 제네릭이나 오버로드로 얽힌 참조처럼 grep이 놓치는 연결도 그대로 잡아낸다.

앞서 겪은 오탐은 정확히 이 지점에서 갈렸다. 텍스트 탐색은 실제로 쓰이고 있던 export의 연결을 찾지 못했다. serena는 타입 체커가 해석한 참조 그래프를 그대로 보기 때문에 이 연결을 그대로 잡아낸다.

후보를 찾은 뒤 별도로 재검증하는 단계를 따로 얹지는 않았다. 참조 여부를 판단하는 탐색 자체를 grep 기반에서 serena 기반으로 바꿨다.

검색 방식이 바뀌면서 토큰 사용에도 차이가 났다고 본다. grep 기반 탐색은 후보를 찾을 때마다 관련 코드를 통째로 읽어 들여서 그 내용을 다시 훑어야 했는데, serena는 LSP 메서드 호출 하나로 참조 목록만 받아온다. 파일 전체를 컨텍스트에 올리지 않고 필요한 참조 지점만 오가기 때문에, 같은 감사 작업이라도 컨텍스트에 쌓이는 토큰이 줄어드는 셈이다.

## Stop 훅 도입

serena로 참조 탐색 자체는 정확해졌지만, 검증이 걸리는 시점은 여전히 PR을 만든 뒤였다. 그래서 Claude Code가 한 턴을 마칠 때 lint, prettier, 타입체크를 돌리는 Stop 훅을 추가했다.

이 훅은 감사 워크플로우뿐만 아니라 평소 직접 개발할 때에도 도움이 됐다. 커밋하기 전, PR을 만들기 전 시점에 걸리는 검사라서 CI나 리뷰에서 잡히기 전에 문제를 먼저 줄여준다.

## GitHub App 도입

CI가 안 돌았던 원인을 팀원이 짚어줬다. GitHub Actions는 재귀 실행을 막으려고, `GITHUB_TOKEN`으로 만든 PR에서는 `pull_request` 이벤트로 새 워크플로우를 트리거하지 않는다. `workflow_dispatch`나 `repository_dispatch`처럼 명시적으로 호출하는 이벤트만 예외다.

팀원이 제안한 방법은 PR을 만들 때 `GITHUB_TOKEN` 대신 GitHub App의 installation access token을 쓰는 것이었다. `actions/create-github-app-token` 액션으로 App ID와 private key를 시크릿에 저장해두고 토큰을 발급받아 PR을 만들면, PR을 만든 주체가 `github-actions[bot]`이 아니라 등록해둔 App이 되기 때문에 `pull_request` 워크플로우가 정상적으로 트리거된다.

이 방법을 적용한 뒤로 감사 워크플로우가 만든 PR에도 CI가 정상적으로 돈다.

## 달라진 점

이렇게 해놓으니 요청이 계속 바뀌는 와중에도 코드가 그대로 쌓이지 않는다. 세 워크플로우가 각자 역할에 맞춰 주기적으로 죽은 코드와 컨벤션 어긴 파일을 걸러내고, Stop 훅과 CI가 그 결과를 두 단계로 다시 검증한다. 손으로 따로 시간을 내지 않아도 코드베이스가 정리된 상태로 유지된다.
